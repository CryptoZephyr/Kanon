# Kanon Architecture Boundary

Canonical source: [Kanon Architecture in Notion](https://app.notion.com/p/3cac53818312815b9be4f4bb67232d16).

Kanon separates wallet ownership, delegated agent authority, application state, and autonomous execution.

- `packages/manifest` will parse and identify agent release capability declarations. A manifest never grants authority.
- `packages/permissions` normalizes the Privy-backed company terms, derives deterministic `permissionHash`, and classifies authority changes with proof-backed coverage.
- `packages/privy` contains the vendor-specific wallet, policy, signer, execution, and revoke adapter. Its policy compiler is execution-method aware. `eth_sendTransaction` receives only the verified stateless controls. `eth_signTransaction` may also receive the verified rolling-value aggregation reference, then the signed transaction is broadcast separately.
- `packages/ens` contains the vendor-specific ENSv2 identity, resolver, access-control, approved-state, and resolution adapter. T6 proved the live Sepolia hierarchy and protected writer boundary. T7 binds that identity to normalized names, node, resolver, control wallet, and protected approved-state readback. The adapter fails closed on resolver provenance, node mismatch, stale lifecycle, inactive Privy authority, or mismatched release and permission hash.
- `packages/shared` holds the installation lifecycle contracts, exact human-decision binding, delegated Privy authority binding, verified ENS approved-state binding, execution evidence, and revocation evidence. It does not hold secrets or owner credentials.
- `apps/runner` creates a short-lived delegated execution context from an active installation. It re-reads installation state before every execution, refuses stale, revoked, unverified, or mismatched bindings, and passes only delegated wallet, signer, policy, method, and request data to the executor.

The live T11 to T13 lifecycle proof confirms the cross-plane ordering. Initial activation requires exact human approval, delegated Privy authority, and ENS approved-state readback before the runner executes. An expanded update must obtain a new approved decision and prove the new Privy policy before the four ENS protected records advance. Revocation removes the delegated signer first, proves later delegated execution fails, then changes only `kanon.status` to `revoked` through the authorized ENS writer. The persistent name and historical identity records remain resolvable.

Privy controls financial execution. ENSv2 provides the company-controlled identity and namespace plane. Durable application state cannot claim active authority without verified required control configuration. A compiler input that asks a selected Privy method to enforce an unavailable restriction fails with `UNSUPPORTED_POLICY_COMBINATION`. Kanon never substitutes an application-only counter or a weaker policy. T14 freezes the versioned backend/API data contract in `packages/shared/src/api-contracts.ts`, including company-authenticated routes and stable projections for organization, wallet, agent capability, company terms, approval, active authority, evidence, update diff, and revoke. The projections exclude private keys, owner credentials, and owner quorum material. No API server or frontend implementation is present in this phase.

An installation can become `ACTIVE` only after an exact approved human decision, active delegated Privy authority, and verified ENS approved state agree on the release and `permissionHash`. An update with expanded, substituted, or unknown authority remains pending until a new exact reauthorization decision is recorded. The isolated runner has no owner fallback. A stale generation or revoked binding is refused before the delegated executor is called.
